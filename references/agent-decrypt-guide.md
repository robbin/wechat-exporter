# macOS WX 数据库解密思路设计

## 1. 目标与范围

目标读者是一个从零动手的 coding agent：没有参考源码、没有历史对话，只拿到这份文档，也能写出可运行、可自证正确的解密实现，并且知道哪一步可以宣称成功、哪一步不能。

这个承诺的适用范围要说清楚：拿到密钥之后的部分——页面格式、认证、逐页解密、WAL、验收——是完整可实现的；取得密钥的部分只对第 5.2 节的形态 A 完整，形态 B 需要针对具体版本另行分析，第 5.3 节只给原理与参数，不保证够用。

范围是 macOS 上 WX 4.x 的本地 SQLCipher 数据库，即其数据根目录下 `db_storage` 里的 `.db` 文件。不涉及服务端、不涉及其他键值存储格式、不涉及自动发布、不提供绕过系统保护的通用手段。自写完整的 WAL 恢复器也不在范围内：第 8.4 节只给受限恢复路线，完整恢复走第 8.5 节。

还要区分两件事：把密文还原成标准 SQLite 文件，与把 SQLite 读成可阅读的聊天记录，是两层工作。表结构、正文编码或压缩、联系人与附件的关联，都不在本文范围内；解密成功不等于拿到可直接阅读的记录。

整件事的核心不是破解 AES，也不是猜登录密码，而是取得客户端本来就持有的数据库密钥，再按页面格式逐页还原：

```
合法取得密钥 → 与数据库匹配并验证 → 逐页认证并解密 → 恢复标准 SQLite 布局
```

需要的是 32 字节的 AES 密钥 `enc_key`，不是登录密码。不同账号、不同库的密钥和 salt 都可能不同，必须逐库验证。

## 2. 总体流程与里程碑

| 阶段 | 输入 | 输出 | 完成判据 |
| --- | --- | --- | --- |
| 1 定位数据 | 无 | 账号目录、`db_storage` 路径 | 至少找到一个非明文 `.db` |
| 2 采集身份 | `.db` 文件 | 文件标识 + `salt → 候选密钥` 索引 | 每个库都取到 salt；不假设跨文件唯一 |
| 3 取得密钥 | salt 列表 + 运行中的客户端 | `salt → enc_key` 映射 | 至少一个库第一页 HMAC 通过 |
| 4 建立一致副本 | 运行中的客户端 + 密钥 | 同一时点的主库与 `-wal`（`-shm` 可缺） | 已建立一致副本才算通过；不一致的输入不得进入快照恢复验收 |
| 5 恢复快照 | 一致副本 | WAL 已处理的密文主库 | 按第 8.5 节的判据确认已全部回填 |
| 6 逐页解密 | 密文主库 + enc_key | 标准 SQLite 文件 | 全页 HMAC 通过、尺寸一致 |
| 7 验收 | 全部产物 | 报告 | 第 9 节的三层判据，含独立内容比对 |

顺序不能颠倒，原因是第 5 步会改写主库，必须先于解密：默认路线是先把一致副本里的 WAL 交给 SQLCipher 处理，再去解密那份已经处理过的主库。跳过第 5 步、只解密未合并的主库，属于可选诊断分支，不能当作完整恢复的成功条件——部分回填的主库不保证能独立通过结构检查。（顺序上还有一层：先在客户端运行时取得密钥，再停止写入并复制，见第 3.4 节。）

一致副本是默认路线的硬门槛，不是可以带着标签绕过的条件：无法保证一致时，可以继续做显式诊断或恢复尝试，但结果不得通过第 9 节的"快照恢复通过"验收。停写要覆盖整个复制过程，而不是复制开始前检查一次就算。

第 6 步的正确性不依赖第 3 步的实现细节，所以可以先用合成数据把第 6 步做完（第 10 节），再去解决密钥来源。

## 3. 前置条件

### 3.1 定位数据目录

不要硬编码路径。容器目录名与数据根目录名由开发商决定，可能随版本变化，用发现代替记忆：

```bash
find ~/Library/Containers -maxdepth 6 -type d -name db_storage 2>/dev/null
```

任何形如下面的路径都是候选，其中方括号部分按实际发现结果替换：

```
~/Library/Containers/[容器标识]/Data/Documents/[数据根]/[账号目录]/db_storage/
```

一个容器标识下可能出现多个账号目录，必须全部遍历，写死账号名会漏。

目标进程名（即其可执行文件名）与应用包主体名一致，用 `ls /Applications` 与 `pgrep -lf` 对照即可确定，不必记忆。

数据根下还有若干子目录与多种扩展名：除了 SQLite 数据库，还有键值存储、缓存与物料文件。实现只需递归遍历，处理所有 `.db` 及其同名 `-wal`/`-shm`，其余后缀一律跳过——它们要么是明文，要么属于另一套键值格式，不能按 SQLCipher 处理。

因此不要把目录名或扩展名写进代码，按后缀过滤即可：目录结构随版本变化，写死会失效。

### 3.2 内存可读性：前提、判据与代价

从运行中的进程取密钥有两个硬前提，缺一不可。本节说明前提、判据与代价；命令只作为说明，是否执行取决于使用者的授权范围与风险判断。

第一，调用方需要 root 权限。

第二，目标进程必须处于不带 Hardened Runtime 的签名状态。先看当前状态：

```bash
codesign -dv --verbose=2 /Applications/[目标客户端].app 2>&1 | grep -E "flags|TeamIdentifier"
```

标志为 `flags=0x2(adhoc)` 且没有团队标识时，内存读取在 SIP 开启的情况下也能工作（实测 `csrutil status` 为 enabled 时成立）。若标志显示进程受运行时保护，在确认授权后可以这样处理：

```bash
sudo codesign --force --deep --sign - /Applications/[目标客户端].app
# 然后退出并重启客户端；客户端每次自动更新后都要重做
```

副作用不止"少了一层保护"：应用签名标识变了，已绑定的钥匙串项目、系统权限授权（麦克风、屏幕录制、辅助功能等）、随包更新都可能受影响，需要重新授权或重新登录。上面这条命令和"root 加 adhoc 就能读内存"一样，都是特定环境下的经验，不构成对所有 macOS 版本与客户端版本的保证。另一条代价更大的路线是关闭 SIP 并用调试器附加，本文不展开。

单独写这一节的理由：它决定第 5 节能不能走通，而它的失败表现（`task_for_pid` 直接返回非 0）与密钥错误完全不同，提前判断比事后排查便宜。

### 3.3 工具链

只要能读进程内存、能做 AES-CBC 与 PBKDF2-HMAC-SHA512、能读 SQLite 即可，语言不限。

- 内存扫描：C 直接用 `mach/mach_vm.h`（`task_for_pid` / `mach_vm_region` / `mach_vm_read`）最省事；Go、Rust 需 FFI；Python 可走 lldb 的 `SBProcess.ReadMemory`。
- 加密：Python 用 `hashlib.pbkdf2_hmac` 加任意 AES 库；macOS 上也可用 CommonCrypto 的 `CCCrypt`，无需第三方依赖。
- 交叉验证：`brew install sqlcipher`，用于独立确认密钥与数据。

### 3.4 安全要求

密钥与解密后的明文都不得进入日志、提交记录或对外输出。只处理稳定副本：先取证，再解密，不要一边让客户端写入一边逐页读。原始库不得被覆盖。第 8 节的 WAL 操作会改写密文主库，必须在副本上做。

"稳定副本"比"先复制一次"更严格。复制完成之后文件不再变化，不等于复制到的那几个文件属于同一个时点：主库与 `-wal` 若取自不同时刻，两边各自都可能是真实且 HMAC 正确的页，组合起来却是错的。客户端正在写的时候，用户态没有绝对安全的取得办法，可行的前提是先停止写入，再把同一时点的主库与 `-wal`、`-shm` 一次性复制并记录时点；同卷只读快照（例如 APFS 本地快照）也能给出一致视图。还要注意，客户端正常退出并不保证 WAL 已合并。若做不到，产物只能留作诊断，不得通过快照恢复验收。停写要覆盖整个复制过程，只确保复制开始前没人写是不够的。

顺序上，先在客户端运行时取得密钥，再停止写入并做一致复制；反过来会拿不到内存里的密钥。

## 4. 采集库身份

对每个大小不小于 4096 字节的 `.db`，读前 16 字节：

- 开头是 `SQLite format 3\0`，说明是明文库，跳过。
- 否则这 16 字节就是该库的 salt。

salt 不是秘密，也不能单独用于推导密钥；匹配上 salt 本身不足以证明密钥正确，它只用来缩小候选范围。

密钥候选必须按 salt 索引，不能拿相对路径当键。这是最容易踩且最难发现的坑：同名的相对路径（例如 `message/0.db` 这种）在每个账号目录下都存在，用相对路径建映射时后写的一条会覆盖前一条，结果是另一个账号的库拿到错误密钥，而任何"遍历完成、文件已生成"的日志都不会报错。

实测后果：密钥映射里"看起来全都有"，因为每个相对路径都查得到值；实际有一批库拿到的是另一个账号的密钥，复查时正好一半全页 HMAC 通过，另一半在第一页就失败，失败的正是与成功账号重名的那些路径。

也不要把 salt 升级成文件身份：salt 不保证跨文件唯一，数据库的复制品会共用同一个 salt。三件事要分开表达：物理文件身份用账号加相对路径，密钥候选索引用 salt，验证结果与输出路径逐文件记录。输出路径同样要保留账号隔离，否则修好了密钥映射，解密文件仍会互相覆盖。

## 5. 取得密钥

### 5.1 先判定版本分支

不判定分支就动手，会在第一页 HMAC 上反复失败却不知道原因。两种已知形态：

| 形态 | 表现 | 密钥如何得到 |
| --- | --- | --- |
| A，4.0.x 及部分 4.1.x | 进程内存中存在 ASCII 串 `x'<64位hex><32位hex>'`，前 64 位是 enc_key，后 32 位是对应 salt | 直接取出，不再派生 |
| B，4.1.10 起已有报告 | 内存中不再缓存 raw enc_key，只缓存 passphrase | `enc_key = PBKDF2-HMAC-SHA512(passphrase, salt, 256000, 32)` |

判定只能靠实验：按分支 A 扫一遍，逐个候选做第一页 HMAC 校验。只要有一个候选通过就是 A；完全扫不到 salt 匹配的候选，才考虑转分支 B。不要靠版本号猜，版本号与实际行为并不严格对应。

扫不到也不等于一定是分支 B：权限不足、扫错了进程、目标库还没被客户端加载、扫描范围或分块重叠量不对，都会给出同样的空结果。先把第 11 节里这几项排除，再换分支。

### 5.2 分支 A：内存扫描

```
pid = pgrep -x [目标进程名]
task_for_pid(mach_task_self(), pid, &task)          # 需要 root
addr = 0
while mach_vm_region(task, &addr, &size, VM_REGION_BASIC_INFO_64, ...) == KERN_SUCCESS:
    if 区域可读（建议要求 READ|WRITE 同时具备）:
        for 每块 CHUNK（2–8 MiB，按区域边界截断）:
            data = mach_vm_read(task, 块起始, 块长度)
            在 data 中查找模式：b"x'" + 96 个 hex 字符 + b"'"
            候选: enc_key = hex 前 64 位, salt = hex 后 32 位
        步进时保留 99 字节重叠
    addr += size
```

几个条件各自对应一种会漏候选的真实情况：

- 模式总长 99 字节（`x'` 两个字节 + 96 位 hex + 收尾单引号）。跨块匹配所需的最小重叠是 98 字节（模式长度减 1），取 99 更直观；低于 98，在最坏情况下会漏掉跨边界的候选。标准形态的覆盖承诺只针对成功读到的那些区域，本文不做跨区域拼接。
- 只扫可读写区域，跳过只读与可执行区域，噪声更少。
- hex 比较前统一转小写。
- 候选按 `(enc_key, salt)` 去重，重复是常态。
- 除 96 位十六进制的标准形态，还可能遇到两种变体：只有 64 位（只含 key，需与全部 salt 逐个试）、长度大于 96 位且为偶数（取前 64 位为 key、后 32 位为 salt）。完整覆盖的承诺只针对标准形态；变体是尽力扫描，因为变长模式配固定的分块重叠量无法保证不漏——要认真支持变体，就得给候选长度设上限，并单独处理跨块与跨区域的匹配。变体最终一律以 HMAC 校验为准。
- 这一步是纯字符串匹配，与指针宽度无关，32 位与 64 位进程共用同一套逻辑。

### 5.3 分支 B：passphrase 派生

拿到 passphrase 有两条路：用 lldb 在 `CCKeyDerivationPBKDF` 上下断点，触发客户端打开数据库（例如退出登录再重新登录一次），从调用参数里取输入；或对二进制做静态分析定位读取位置。两条路都强依赖具体版本，属于升级就要重做的部分，本文不给固定脚本。拿到之后每个库的派生都相同：

```
enc_key = PBKDF2-HMAC-SHA512(passphrase, 该库自己的 salt, 256000, 32)
```

salt 是每个库各自的前 16 字节，不是全局常量。

### 5.4 唯一判据

无论走哪条分支，都不能用"找到了""格式对"当成功条件。唯一判据是按第 6 节公式算出第一页 HMAC 并与文件中存储的 64 字节一致。一个候选只对某个 salt 的库成立，必须逐库验证。

### 5.5 只在被加载过的库里有缓存密钥

实测存在这样的加密库：在内存中完全找不到对应候选，原因是客户端还没打开过它，密钥自然不在缓存里。所以"扫描完成"不等于"所有库都能解密"：输出必须逐个库标注是否拿到密钥，并明确列出缺失项。

`-wal` 非空的库通常说明它被打开过，可以据此提高命中率，但不能作为保证。

## 6. 页面格式规范

以下常量与公式可以直接照抄。

| 项目 | 值 |
| --- | --- |
| 页面大小 | 4096 字节 |
| 加密算法 | AES-256-CBC |
| 密钥长度 | 32 字节 |
| 每页 IV | 16 字节 |
| 每页认证值 | HMAC-SHA512，64 字节 |
| 每页尾部保留区 | 80 字节 = IV(16) + HMAC(64) |
| 每页可用空间 | 4016 字节 |
| 页码编码 | 4 字节无符号小端，从 1 开始 |

区间均为左闭右开，相对于当前页：

| 页面 | salt | 密文 | IV | HMAC |
| --- | --- | --- | --- | --- |
| 第一页 | `[0,16)` | `[16,4016)` | `[4016,4032)` | `[4032,4096)` |
| 第二页起 | 无 | `[0,4016)` | `[4016,4032)` | `[4032,4096)` |

认证密钥派生：

```
mac_salt = salt 每个字节 XOR 0x3a
mac_key  = PBKDF2-HMAC-SHA512(enc_key, mac_salt, iterations=2, dkLen=32)
```

两种形态在拿到 enc_key 之后，都按上面的公式派生 mac_key；这里的 2 次迭代只属于这一步。分支 B 里的 256000 次迭代是另一件事，那是 passphrase 到 enc_key 的派生，不要与这里混用。mac_key 只用于认证，不用于 AES。

页认证值：

```
start  = 16 if 页码 == 1 else 0        # 第一页的 salt 不参与认证
input  = 本页[start : 4032] || 页码(4 字节小端)
值     = HMAC-SHA512(mac_key, input)
```

认证输入是"密文与 IV 的拼接"再接上页码：页码在被认证的数据里面，不是认证结果的附加物；算出的 64 字节存放在 `[4032,4096)`。这一处的括号位置容易写错，写错的表现是第一页恒不通过。

这是实现时最容易错的一条：第一页必须从 16 开始，否则第一页永远验不过，而后续页与整库解密可能完全正常，会让人误判成密钥错误。这是最常见的实现错误（附录 A）。

## 7. 逐页解密

```
把输入按 4096 字节切页，页号从 1 开始
对每一页：
    iv = page[4016:4032]
    if 页号 == 1:
        plain = AES-CBC-Decrypt(enc_key, iv, page[16:4016])   # 4000 字节
        out   = b"SQLite format 3\x00" + plain + b"\x00" * 80
    else:
        plain = AES-CBC-Decrypt(enc_key, iv, page[0:4016])    # 4016 字节
        out   = plain + b"\x00" * 80
```

必须遵守的约束：

- 每页是独立的 CBC 单元，使用本页自己的 IV。不能把整个文件当成一条连续 CBC 密文。
- 不做 PKCS#7 去填充。密文已按固定页布局对齐，4000 与 4016 都是 16 的倍数。
- 尾部 80 字节必须补齐为 4096 字节一页，不能删除，也不能把 SQLite 文件头偏移 20 的保留字节数改成 0。B-tree 与页内偏移是按每页 4016 字节可用空间建立的。填零即可，SQLite 不读保留区。
- 文件长度不是 4096 整数倍时先调查原因。补齐最后一页能让解密跑完，但该页的 HMAC 无法通过验证，只能标记为已知不完整，不得算作验收通过，也不要静默补零。
- 每一页都必须先通过该页的 HMAC，才能采纳它的解密输出。上面的伪码只写了计算，没写这道闸门。
- 全零页的 HMAC 必然失败，遇到时不要当成密钥错误，也不要默认它就是未分配页：它也可能是被截断或未写入的页。跳过的前提是能解释成因；跳过就意味着产物带有缺失标记，属于恢复结果，不满足第 9 节的严格验收。实测样本中未出现。
- 任何一页认证失败后，都不要把半成品当正式产物交付：应输出带失败标记的恢复产物，并逐页说明哪些页没有通过。
- 第一页解密后应校验：偏移 `[16,18)` 的大端页大小为 4096，偏移 20 的保留字节数为 80。不符说明格式假设错了，要查原因，不要直接改字段。

## 8. WAL

### 8.1 为什么必须处理

实测绝大多数 `.db` 都存在同名 `.db-wal`。忽略 WAL，就可能在报告里宣称"已导出最新数据"，而实际缺了最新事务。WAL 处理分两条路线：第 8.5 节让 SQLCipher 代办，这是能支撑"完整且最新"声明的默认路线；第 8.4 节自己解析并重放，只作为受限恢复路线。

### 8.2 结构

结构如下（本机实测到 magic `0x377f0682`、page_size 4096；`0x377f0683` 是同族的格式支持值，未实测）：

| 区域 | 长度 | 是否加密 |
| --- | --- | --- |
| WAL 头 | 32 字节 | 明文 |
| 帧头 | 24 字节 | 明文 |
| 帧页 | 4096 字节 | 非页 1 帧与普通页相同的加密布局；页 1 帧见下文 |

WAL 头逐字段（偏移从 0 起，整数字段均为大端）：

| 偏移 | 宽度 | 字段 |
| --- | --- | --- |
| 0 | 4 | magic |
| 4 | 4 | 格式版本，实测值为 `3007000`；其他值按不支持处理，不要猜 |
| 8 | 4 | page size |
| 12 | 4 | checkpoint 序号 |
| 16 | 4 | salt1 |
| 20 | 4 | salt2 |
| 24 | 4 | 头校验和 1 |
| 28 | 4 | 头校验和 2 |

帧头逐字段（偏移相对于帧起点，同样是大端）：

| 偏移 | 宽度 | 字段 |
| --- | --- | --- |
| 0 | 4 | pgno |
| 4 | 4 | dbsize，非 0 表示这一帧是提交帧 |
| 8 | 4 | salt1 |
| 12 | 4 | salt2 |
| 16 | 4 | 校验和 1 |
| 20 | 4 | 校验和 2 |

帧从 WAL 头的第 32 字节开始，第 n 帧（n 从 1 起）的起始偏移是 `32 + (n - 1) * (24 + page_size)`。帧不是按 page_size 对齐的，两帧之间没有填充。

这里有一个必须区分的字节序：WAL 头与帧头的整数字段按大端读，而算页 HMAC 时用的 pgno 要按 4 字节小端编码。第 6 节的"页码小端"只适用于后者，套到帧头解析上会读错。

帧页的认证，当 `pgno != 1` 时：认证输入是帧页的 `[0:4032]` 再拼接 pgno（4 字节小端），结果为 HMAC-SHA512，存储在 `[4032,4096)`。pgno 取自帧头，不是帧序号；实测把 pgno 当成帧序号算，HMAC 必然不匹配。

pgno 为 1 的帧另论：它的帧内布局、认证范围与 CBC 解密范围，本机都没有验证。不要套用普通页的规律去推断——试出认证范围不等于确定了解密范围。遇到这类帧就转第 8.5 节，或报告不支持。

### 8.3 一个必须记住的反例

实测源 WAL 的第一帧：HMAC 验证通过，解密后第一字节是合法的 B-tree 叶子页类型，看起来完全可用。但它的 salt 与 WAL 头的 salt 相差 1，属于上一次 checkpoint 之后的残留帧，不应当被重放。

结论：HMAC 通过只能证明这页是真的，不能证明这页应当生效。salt 一致性检查不可省略。

### 8.4 受限恢复：自己重放 WAL

先说结论：这一节的流程不实现 SQLite 的滚动校验和链，因此不能支撑"完整且最新"的声明。它能做的是在明确标注的前提下，把通过现有检查的候选前缀里已提交的页补进主库。风险不只是结果可能偏旧：事务组合或最终库大小也可能错。

硬性前提：需要完整重放、或需要对外宣称数据完整最新时，改用第 8.5 节；用本节路线得到的产物必须标注为受限恢复，并在报告里写明"未校验 WAL 内部一致性，结果可能不是最新状态"。

```
读 WAL 头；page_size 不是 4096、magic 不是 0x377f0682 或 0x377f0683 → 不支持，停止
从偏移 32 开始按 24 + page_size 遍历帧：
    帧头 salt1/salt2 与 WAL 头不一致 → 候选前缀到此结束
    pgno 为 1 → 转第 8.5 节，或结束受限路线并报告不支持
    该帧页 HMAC 不通过 → 停止
    记录 (pgno, dbsize)
提交点 = 最后一个 dbsize != 0 的帧
重放第 1 帧到提交点这一帧（含提交点这一帧）；提交点之后的帧一律不生效
按 pgno 覆盖主库对应页；同一 pgno 出现多帧时取靠后的那一帧
若提交点的 dbsize 与主库页数不同，以 dbsize 为准截断或扩展
没有提交点 → 不重放任何帧，报告"无已提交帧"
```

最容易写错的是提交点那一行：提交帧本身属于要生效的事务，必须重放。写成"只重放它之前的帧"就会丢掉最后一个事务，单帧事务会整个丢失。

为什么不能宣称等价。页 HMAC 覆盖的是密文加 IV 加 pgno，它不覆盖帧头里的 dbsize，也不绑定帧在日志中的顺序或与前一帧的关系。因此：

- dbsize 被改坏时，页 HMAC 仍会通过，但提交点或最终库大小已经错了。
- 同一代际内真实帧被重复或重排，salt 检查与逐页 HMAC 也都可能通过。
- WAL 头与被排除在 HMAC 之外的帧元数据损坏，无法用页 HMAC 发现。

校验和链正是用来覆盖这些的，缺了它就只能算受限恢复。想自己实现完整规则，就要补上逐帧滚动的校验和递推以及它的字节序选择。

停止之后怎么定性也要区分开，不能统一写成"扫描结束，成功"：

| 情况 | 定性 | 允许受限产物 | 禁止严格成功 |
| --- | --- | --- | --- |
| 遍历到文件末尾，且最后一帧是提交帧 | 按未经完整校验的提交标记推定的恢复结果 | 是 | 是 |
| 帧头 salt 不匹配 | 候选前缀结束，可能是上一代残留 | 是 | 是 |
| 帧页 HMAC 不通过 | 认证失败，原因待判（可能是损坏，也可能是布局假设不成立） | 是，需写明原因待判 | 是 |
| 末尾是完整但未提交的帧 | 正常情况：忽略提交点之后的完整尾部，不算损坏 | 是 | 是 |
| 帧头或页体不足一个完整帧 | 截断，候选前缀终止 | 是，需报告 | 是 |
| pgno 为 0 或超出 32 位可表示范围 | 格式不合法，拒绝该前缀 | 否 | 是 |
| 扩展输出时缺页 | 页数据不完整，拒绝该前缀 | 否 | 是 |

读法：受限恢复路线永远不能通过第 9 节的严格验收，它只能产出带标记的恢复产物。表中差别在于某一行还能不能产出受限产物：最后两行连受限产物也不产出。

关于 dbsize 有三件事，必须分开，不要合成一个条件：

- 帧页码的格式范围：pgno 必须大于 0，并且能放进 32 位无符号整数。
- 提交帧的数据库大小：只有 dbsize 非 0 的帧带提交语义；非提交帧的 dbsize 为 0 是正常编码，不能当异常。
- 最终输出页数：由最后一个提交帧的 dbsize 决定。历史上出现过更大的页码不算错误——先大库后缩库时，早期帧的 pgno 会超过最终页数，按最终页数截断即可，不要因此拒绝整个前缀。

### 8.5 默认路线：交给 SQLCipher

在副本上让 SQLCipher 自己判定，不要重写 SQLite 的 WAL 逻辑：

```bash
cp [库].db [库].db-wal [库].db-shm /tmp/copy/     # 必须在可丢弃的副本上操作
```

`-shm` 不存在不是错误，SQLite 会自行重建，不要要求三件套必然齐全。副本到位后：

```bash
sqlcipher /tmp/copy/[库].db "PRAGMA key = \"x'[enc_key][salt]'\";
  PRAGMA cipher_compatibility = 4; PRAGMA cipher_page_size = 4096;
  PRAGMA wal_checkpoint(PASSIVE);"
```

关于 `PRAGMA wal_checkpoint(...)` 的返回值，有一个反直觉的地方，实测确认：

| 模式 | 调用前 WAL 中的帧数 | 返回值（busy, log, checkpointed） |
| --- | --- | --- |
| PASSIVE | 5 | `(0,5,5)` |
| FULL | 5 | `(0,5,5)` |
| RESTART | 5 | `(0,5,5)` |
| TRUNCATE | 5 | `(0,0,0)` |

三点读法：

- TRUNCATE 成功后会先把 WAL 截断再报告结果，后两列恒为 0，不能拿来推断"执行前有没有待合并帧"。
- PASSIVE 也是 checkpoint，同样会把可安全回写的帧写回主库，只是不等待读者、不阻塞；不要以为它不动主库。
- 第二列是调用时 WAL 中的帧数，它不扣减已经回填过的部分，所以不等于"仍需合并的帧数"。实测里被读者挡住的那次 log 仍是 5，实际只回填了 3 帧。

因此所有 checkpoint 都只在可丢弃副本上做。接受判据按下面的顺序判定，不要自己在几条之间取舍（实测确认）：

| 返回值 | 含义 | 处理 |
| --- | --- | --- |
| `(0,-1,-1)` | 不是 WAL 模式，没有待合并的 WAL | 可直接解密主库 |
| busy = 1 | 被读者或锁挡住，没有完成 | 算失败，不能当作已合并 |
| `log == checkpointed` | 调用时 WAL 中的帧已全部回填 | 可以进入下一步 |
| `log > checkpointed` | 只回填了一部分 | 不能当作完整合并结果 |
| SQL 报错 | 调用本身失败 | 算失败，报告原始错误 |

顺序是：先看 SQL 报错与不支持状态，再排除 busy 非零，然后单独解释 `(0,-1,-1)`；普通成功分支要求 busy 为 0，且两个计数非负、相等。其他未列出的组合一律不进入完整恢复的下一步。

还要注意，`(0,-1,-1)` 只说明当前连接看到的是非 WAL 情形，它不能证明采集时没有漏掉 WAL。输入完整性靠第 3.4 节的一致副本和源文件清单来保证，不是 checkpoint 返回值能证明的事。

实测依据：先用一个持有旧快照的读者钉住位置，再写入两帧，PASSIVE 返回 `(0,5,3)`——busy 为 0，却只回填了 3 帧；同样条件下 FULL 与 RESTART 返回 `(1,5,3)`。所以 busy 为 0 不足以证明全部回填，必须比较 log 与 checkpointed。

副本上不要有其它连接（包括别的检查工具）同时打开，否则会持续挡住回填。做不到全部回填时，按失败退出并把状态写清楚，不要把"部分合并的结果"当成完整结果交付。

另外把"完整且最新"的含义限定清楚：它指的是所采集的那份一致快照中，SQLite/SQLCipher 判定为有效的已提交状态。它不等于客户端此刻的最新状态，也不意味着对快照之前的全部事务做完备取证。

checkpoint 完成后，以那份被 checkpoint 过的副本作为解密输入。

### 8.6 两种比对实验与输出目录

"有没有未合并数据"与"自写重放是否可靠"是两个不同的问题，要用两个实验分别回答，不要混在一条判据里。

实验一，忽略 WAL 会丢什么：

- 副本甲：保留 `-wal` 与 `-shm`，按 8.5 节处理后解密。
- 副本乙：去掉 `-wal` 与 `-shm` 后解密。
- 两者比较，得到的是两份输入的逻辑状态差异，可能是新增、更新或删除，不要一律说成"丢掉了内容"。未合并的主库不一定能独立通过结构检查，无法比较时按"未合并状态不可比较"报告，不要强行逐表比对。

实验二，自写重放是否与独立实现一致：

- 副本甲同上。
- 副本乙：按 8.4 节重放后解密。
- 两者比较。这一实验只回答"自写重放在这个样本上是否与 SQLCipher 的结果一致"，不能用来判断有没有未合并数据：如果 WAL 里确实有更新且重放正确，两边本来就应当相同。

两点效力边界：如果"重放后"的结果来自尚未验证的自写重放器，两边相同也可能意味着重放器什么都没做，此时只有以 SQLCipher 的结果作基准，比对才有证明力；即使逻辑内容完全一致，也只说明比较过的内容没有差异，不能证明 checkpoint 之前不存在待回填的帧。

输出目录要保持清洁：不要把源目录的 `-wal`/`-shm` 复制到解密输出目录。解密后的主库旁边若存在未解密的 WAL，SQLite 会尝试读取它，导致报错或读到脏数据。实测输出目录里出现的 0 字节 `-wal` 是 SQLite 自身创建的，无害，但不是主动复制过去的。

## 9. 验收

成功要分三层，不能一句话带过：

| 层级 | 必须证明的事 |
| --- | --- |
| 主库解密通过 | 所有应认证的主库页全部通过；页面布局与结构检查通过 |
| 快照恢复通过 | 在一致输入上正确处理了有效且已提交的 WAL，并写明恢复的是哪个时点的快照 |
| 目标范围全部处理并报告 | 所有账号、所有目标库都有结论；成功、缺密钥、失败、不支持、跳过、受限恢复各自列出。这一层不表示全部恢复成功 |

主库解密这一层必须同时满足：

1. 全页 HMAC 通过，不只是第一页。任一页失败都要报告失败原因（密钥错误、快照不一致、文件损坏、版本差异），不得跳过继续写"成功"。
2. 解密这一步的输入输出大小一致，且都是 4096 的整数倍。默认路线的比较对象是 checkpoint 之后的密文主库；跳过第 5 步的诊断分支要单独说明，不能拿未合并主库的大小去要求相等。
3. 用普通只读 SQLite 检查：`PRAGMA integrity_check` 必须返回 `ok`，并能列出 `sqlite_master` 中的对象。
4. 与独立读取的结果做内容比对，而且必须在同一稳定快照的同一逻辑视图上比：
   - 只比对象数量或行数只能支撑有限结论，撑不起"内容一致"。
   - 声称全库一致，就要做全库逻辑内容比对（逐表导出后比对摘要），不能靠抽样。
   - 拿带 WAL 的库去验证"未合并 WAL 的主库输出"不是同视图比对，两边必须先调整到同一状态。
   - 比对要保留值类型与 BLOB 的原始字节，不要用文本拼接判等。
   - 比对要有确定性：按对象定义集合比，无自然顺序的表先指定排序键，重复行必须保留，不能先去重再比。
   - 独立读取要来自一份不参与 checkpoint 改写的采集快照：默认处理与独立读取各自从该快照建工作副本，并记录源文件清单与 WAL 是否存在。否则两个分支可能共同漏掉 WAL，得到一致的旧结果。

这层拦得住和拦不住什么，也要说清楚。拦得住：错密钥、常见偏移与字节序错误、页尾被删除、多数结构损坏、只补文件头的伪解密。只靠全页 HMAC、结构检查与计数拦不住：遗漏已提交的 WAL 更新、真实旧页覆盖真实新页、内容过期但记录数不变、以及只对成功的部分宣称整体完成。这四种要靠一致副本、第 8 节的 WAL 处理，以及第 4 条的同视图全量内容比对来控制；其中内容过期这一种，同视图的全量内容比对本身能够发现。

不得作为成功依据的东西：文件头是 `SQLite format 3`（这是导出程序自己补进去的）、能看到表名、日志打印了"完成"、`integrity_check` 为 ok（它只能证明结构一致，不能单独作为依据）、对象数与行数相同、个别库通过而其它库没验。

另外两个容易遗漏的条件：使用一致副本（见第 3.4 节），以及正确处理 WAL（非空 WAL 未处理时不能宣称导出了完整最新数据）。

## 10. 用合成数据自测

在碰到任何真实库之前，先把算法闭环。要点是让生成方与校验方来自不同实现，否则加密器和解密器会共用同一个错误假设，自测全绿而实际全错。

不要拿一个普通 SQLite 文件直接改造成密文：普通文件的每页没有预留 80 字节，把尾部换成 IV 与 HMAC 会覆盖有效数据。可行做法是让 SQLCipher 按目标参数生成一个已知内容的库：

```bash
sqlcipher test.db "PRAGMA key = \"x'[32 字节 hex 密钥][16 字节 hex salt]'\";
  PRAGMA cipher_compatibility = 4; PRAGMA cipher_page_size = 4096;
  CREATE TABLE t(x); INSERT INTO t VALUES (1),(2);"
```

用原始密钥形式 `x'<key><salt>'` 时不做口令派生，认证密钥走 2 次迭代，与目标布局一致。随后用自己写的解密器还原它，断言三件事：全页 HMAC 通过、输出能被普通 `sqlite3` 打开且 `PRAGMA integrity_check` 为 ok、表内容与写入内容一致。

不想依赖 SQLCipher 时，退路是合成页：自造 4096 字节明文，但必须把最后 80 字节置零（保留区不参与 B-tree），再按第 6 节加密，最后断言解密回原文。这条往返路线只能算单元测试，不能代替用独立实现做对照验证。它能在几分钟内暴露第一页特殊处理、页码字节序、mac_key 派生、保留区长度这几处错误，不需要真实数据或 root 权限。

对照库里必须专门造一个"内容改了但结构没变"的用例：只更新已有记录的字段值，不增删表和行，提交后再验证恢复结果。它能直接暴露"全绿但数据是旧的"这类假成功，而这正是计数比对拦不住的情况。

必须造出真正留在 WAL 里的已提交更新，否则测不出东西。可行的构造：

1. 确认库确实处于 WAL 模式；写入基线值并让基线完成合并，是否已回填要用检查确认，不要只靠"关闭连接"推断。
2. 重新打开连接，只更新已有记录的字段值，不增删表和行，提交。控制自动 checkpoint，避免这次提交当场被回填，否则测试会空转。
3. 提交后保持连接、不再写入，也不执行 checkpoint；确认复制期间没有别的连接改写源库。用另一个进程直接复制主库与 `-wal`，得到测试副本：主库是旧状态，WAL 视图是新状态。
4. 断言两件事：只解密主库得到旧值；按第 8.5 节处理 WAL 后解密得到新值。旧值或新值断言不成立，说明夹具没构造成功，要判定为测试失败，不能跳过。

还要覆盖这些危险分支：单帧提交、同一页被多次更新、末尾存在未提交帧、库被缩小（dbsize 变小）、残留上一代帧、帧元数据被改坏。每个用例都要写清预期行为，而不是只列名字。特别要写明：dbsize 被改成另一个合法值时，第 8.4 节的受限恢复路线可能根本发现不了——这个用例要证明的是"它不能据此宣称完整"，而不是要求它具备并不存在的检测能力。

## 11. 故障排查

| 现象 | 优先怀疑 |
| --- | --- |
| `task_for_pid` 返回非 0 | 未用 root；客户端未 ad-hoc 重签名；客户端更新后签名被还原 |
| 扫描完一个候选都没有 | 版本已改为分支 B，密钥不再以 `x'...'` 形式缓存 |
| 扫到候选但全部 HMAC 失败 | 候选属于另一个库或另一个账号；分支 B 的派生步骤缺失 |
| 第一页 HMAC 失败、后续页正常 | 第一页认证范围没跳过前 16 字节 salt |
| 全部页 HMAC 失败 | enc_key 错误；salt 与库不匹配；mac_key 派生参数写错 |
| 个别页 HMAC 失败 | 全是零页；文件被截断；读取时源文件正在被写入 |
| 解密成功但 `integrity_check` 不 ok | 保留区长度处理错；保留字节数字段被改；输入不是 4096 整数倍 |
| 某个库拿不到密钥 | 客户端从未打开过该库，密钥不在内存缓存里 |
| 多账号场景下部分库第一页就失败 | 密钥映射用了相对路径，被另一个账号覆盖 |

## 12. 工程要求

- 幂等与可增量：按 `(账号, salt)` 归档密钥，重复运行不覆盖已有的正确密钥。
- 明确的失败面：每个库单独产出成功、失败原因、是否含未合并 WAL。
- 不猜：任何"看起来对"的中间结果都不能替代 HMAC 与 `integrity_check`。
- 不留敏感物：密钥文件权限设为 600，明文目录与密钥文件都不进版本控制，日志不打印密钥与消息正文。

## 附录 A：实测证据

环境为 Apple Silicon Mac，SIP 开启，客户端为 adhoc 签名。

| 验证项 | 结果 |
| --- | --- |
| 页面格式与认证范围 | 按本规范独立重写实现，三个库全页 HMAC 通过 |
| 解密正确性 | 输出与输入字节数一致，`PRAGMA integrity_check` 为 ok，对象数与密文库一致 |
| 第一页陷阱 | 首次实现用 `[0,4032)` 计算第一页 HMAC，全部失败；改为 `[16,4032)` 后全部通过 |
| 多账号路径冲突 | 多账号下相对路径重复，路径键映射丢失条目；另一个账号的库全部第一页失败 |
| 未加载库无密钥 | 存在加密库在内存中无对应候选 |
| WAL 帧结构 | 帧头 24 字节加页 4096 字节；用帧头 pgno 计算 HMAC 可通过，用帧序号计算不通过 |
| WAL 残留帧 | 存在 salt 不匹配但 HMAC 通过的帧，重放会导致错误结果 |
| WAL 未合并判定 | 按两份隔离副本的逻辑结果比对；同一批样本里 checkpoint 返回值不能单独作依据 |
| checkpoint 返回值语义 | 5 帧待合并时 PASSIVE/FULL/RESTART 返回 `(0,5,5)`，TRUNCATE 返回 `(0,0,0)` |
| 部分回填 | 用持有旧快照的读者钉住位置后，PASSIVE 返回 `(0,5,3)`：busy 为 0 却只回填 3 帧 |
| 非 WAL 库 | 非 WAL 模式下 `wal_checkpoint(PASSIVE)` 返回 `(0,-1,-1)` |
| 内存密钥形态 | 存在 `x'<64hex key><32hex salt>'` 形态（分支 A） |

## 附录 B：实现骨架

与语言无关，最小实现需要这些单元：

```
定位数据
  find_accounts() -> [账号目录]
  find_db_files(账号目录) -> [(相对路径, 绝对路径, 大小)]
  read_salt(路径) -> 16 字节 | 跳过（明文）

密钥
  scan_memory_for_key_strings(pid) -> [(enc_key, salt), ...]
  derive_mac_key(enc_key, salt) -> 32 字节
  verify_page(page, mac_key, 页码) -> 布尔
  verify_db(路径, enc_key) -> 布尔，全页

解密
  decrypt_page(enc_key, page, 页码) -> 4096 字节
  decrypt_db(源路径, 目标路径, enc_key) -> 成功/失败

一致副本与快照恢复（默认路线）
  snapshot_copy(主库, -wal[, -shm]) -> 同一时点的副本；建不了一致副本即失败
  keep_source_snapshot(副本) -> 不参与改写的基准快照，供独立读取
  checkpoint(副本, enc_key) -> 按第 8.5 节的完整契约判定（报错与忙状态先失败）

受限恢复（可选，第 8.4 节）
  parse_wal(路径) -> 候选前缀与提交点
  replay_wal(主库页列表, 候选前缀) -> 新页列表 + 受限标记

验收
  check_integrity(路径) -> 结果
  cross_check_with_sqlcipher(库, enc_key) -> 同快照、同视图的内容比对
```
